# What was and was not verified

The honest list, by date. Back to the [README](../README.md).

## What was and was not verified

- Verified: the module and the single-task action deploy and pass Forge's linter, the three tools are unit tested, the same actions work in Rovo chat on the demo site, and the admin page (steps above) shows the app at the new version with the **Tools** switch, *Disabled* until an admin chooses to enable it.
- **Not verified:** a real external client connection (Claude Desktop, Claude Code). It needs a site admin to switch the tools on and an interactive OAuth sign-in, so it has not been run. Step-by-step instructions for a live demo are in [`docs/mcp-demo.md`](mcp-demo.md). The Claude Desktop steps are the standard remote-MCP setup rather than something Atlassian documents for Forge apps, so treat them as untested.
- Rovo shows its own "Please review" card for `CREATE` actions in chat; whether external clients get an equivalent prompt is up to the client.

## The 17 Nov 2026 additions (UDI-DI and serial-range matching, task progress, daily alerts, ward ownership from the graph, import preview)

- **Verified live (demo site, development environment, version 16.0.0):** the upgrade with the two new graph scopes (`read:graph:issue:jira`, `read:graph:project:jira`) went through, and in Rovo chat the agent's `who_handles_ward` answered for the Cath Lab with the team (Team Atlas), each member's open Jira work read from the Teamwork Graph (0 and 0, which agrees with Jira: one person has two assigned issues, both done, the other none) and, correctly, no project (this team has none linked). The app's log shows the call and no error. The matching engine was run against the live openFDA API: 30 demo devices, 208 matches, no failed searches (`scripts/preview/fixtures/demo.json` is that result).
- **Not verified live, and why:** the dashboard itself (the Progress tab, New since yesterday, the Daily alerts dialog and its permission test, the "Who handles this ward" card, the import preview) could not be opened on a real site from the machine used to build this, because its DNS refuses Forge's CDN host (the known problem described in the developer notes; the app is not at fault and nothing on the machine was changed). They are verified in the preview (the real production bundle in headless Chrome under the Forge content policy: 148 screens, no policy violation, no console error, no accessibility violation) and in 800+ unit tests with fakes. **The daily alert's real run, creating tasks as the app user and posting the comment, has not been run on a real site**: it needs a recall that is new since the last look, and importing devices deliberately does not count as news.
- **Production:** the new major version (new scopes) was deployed to production and the production installation on the judge-simulation site was upgraded with the two new graph scopes (the site owner accepted the consent); `forge install list` shows it *Up-to-date*. Later code-only versions reach it by themselves.

## Live run on the demo site, 18 Nov 2026 (after DNS was fixed)

- **Found live, fixed, re-verified live:** the background check was killed for memory (the function dies near 250 MB; it starts at about 110 MB). It now parses each answer as it arrives, keeps at most 150,000 characters of any recall's code text, runs two searches at a time, and matches each group of identical devices once. A 30-device check takes about 35 s; the scheduled daily run is now queue steps (check, then alerts), each with its own 300 seconds, and every openFDA request has a 45-second limit.
- **Verified live:** the dashboard in light and dark; the Progress tab; the device drawer; Daily alerts saved (the app may create issues in MOBL), and **the daily alert ran on its own and created a task (MOBL-130) and posted its comment as the app**; a **1,000-row paste** (105 KB) previewed all 1,000 rows, imported, and the check of 1,030 devices finished with 894 devices needing action (2,342 matches, saved in parts); the real storage error for an existing key is `KEY_CONFLICT`, HTTP 409; three writers under the lock took strict turns; Forge does **not** expire a ttl key within 40 s, so the lock's own expiry is needed.
- **Teamwork Graph, broken and fixed live:** the graph answered "User is not permitted to query this organization" to every call. Cause: Forge sends the installation's context as `X-Query-Context`, and for this app (a Jira + Confluence installation) that is a *Jira* site ARI (`ari:cloud:jira::site/...`), which the graph does not accept; the same person gets their teams with the *platform* site ARI (`ari:cloud:platform::site/...`), checked from the browser. The app now sends the platform site ARI itself (`graphQueryContext` in `src/runtime.js`). Verified live: the Ward teams tab lists the site's teams (AWS Support, Mobile Dev, Team Atlas and others) and the drawer's **Who handles this ward** shows the team and its members. No admin setting was involved; the four scopes are granted under Connected apps, recallradar, Authorization.

## The 18 Nov 2026 additions (concurrency, capacity, stable device ids, per-product matching on real recalls)

- **Verified, with fakes and real recall text:** two writers never overlap under the lock and an expired lock is taken over; an alert record that cannot be read writes nothing (the baseline is never reset); two requests for one task pair create one task; a saved check of 1,500 matches round-trips through its parts, a stale part is never read, an old one-record result still reads; a 1,000-row import writes only what changed and the same list in another order keeps every id; the per-product and exclusion rules are measured on 48 real recalls ([`docs/ACCURACY.md`](ACCURACY.md)); the preview (148 screens, no violation) and the jsdom smoke test cover the new dashboard order, the Daily alerts dialog with its reasons, and the create-all progress and its closed dialog. Code-only versions are deployed to both environments (development 16.4.0, production 4.4.0).
- **Found by three independent technical reviews of this state, and fixed:** a new saved check overwrote the parts of the old one in place, so a reader could mix the two (parts now carry a generation id); a lock whose holder crashed depended on the storage expiring the key (the lock now carries its own expiry); a read error while changing a ward's team dropped every other ward's team (the change now stops); texts such as "lots 12345 are not affected" or "all units from lot 12345" gave *exact* (they stay *likely*); "Dräger" and "Draeger" were different makers (letters with marks are folded); the first-run screen said "a year" for a three-year look-back and left UDI-DIs out of what is sent to the FDA. Their other findings are limits, now written down where they belong: the accuracy set is developer-labelled and mostly trivial negatives, retrieval is not measured, makers have no alias list, and a 1,000-device list plans on the order of 120 to 400 searches that were never run.
- **Not verified live:** the lock against real Forge storage. The code Forge gives for "key already exists" was not seen; a refusal with status 409 or 412, or with the words *exists*, *already* or *conflict*, is read as "held", and any other refusal runs the work unlocked, as before the lock existed, with a warning in the log. A saved check larger than one storage value (the demo hospital's is far smaller, so the parts have only been exercised against the fake storage), how long a 1,000-row import takes on a real site, and the dashboard itself (the DNS problem above).
