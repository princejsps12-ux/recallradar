# How matching works, in detail

The summary is in the [README](../README.md#how-matching-works). This page has each check, every number and the reason for it.

## How each fact is checked

- **UDI-DI.** The device's identifier (a GS1 GTIN of 8, 12, 13 or 14 digits, always compared as 14 digits with leading zeros) is looked for in the recall's code info. The shapes read: GS1 element strings `(01)GTIN(21)serial(10)lot(17)expiry`, labelled lists (`UDI-DI: a(each), b(case)`, `UDI-DI code:`, `GTIN:`, `DI:`) and unlabelled `<DI>/<serial>` and `<model>/<DI>` pairs (these need a correct GS1 check digit, so a random number beside a slash is not taken for one). A number the text ties to the device's own UDI-DI (`(01)...(21)209`) counts as listed at any length, because it names that product's unit directly. The identifiers in an imported device list must also pass the check digit; the ones in recall texts are compared without it, since recalls contain typos of their own. Code: [`src/udi.js`](../src/udi.js).
- **Normalising text.** Everything is lower-cased and split into words at any character that is not a letter or digit. `MMT-1885CLW/00763` and `mmt 1885clw 00763` are the same. Phrases must match **as whole words, in order**, so model `N15` matches `N12/N15/N17` but never `N150`.
- **Manufacturer.** Legal words (`Inc`, `Corporation`, `Ltd`, `GmbH`, `AB`...) are ignored. Two makers match when **all** words of the shorter name appear in the longer one (`Philips` matches `Philips North America Llc`), and at least one shared word is specific. Generic words (`Medical`, `Healthcare`, `Systems`...) alone never match: `Medical Systems` does not match `GE Medical Systems Information Technologies`. Letters with marks are folded first (`Dräger` is `Draeger`). Two names of **one company** also match, from the short list of families in [`src/makerAliases.js`](../src/makerAliases.js): `BD` and `Becton, Dickinson and Company` and `CareFusion` and `Bard`; `Hill-Rom`, `Welch Allyn` and `Baxter Healthcare Corporation`; `Hospira` and `ICU Medical`; `Datex-Ohmeda`, `GE Healthcare` and `GE Medical Systems`; `Covidien`, `Nellcor` and `Medtronic`; `Respironics` and `Philips`; `Maquet` and `Getinge`; and about ten others. A maker belongs to a family when its words contain one of the family's names as whole words (a name of three letters or fewer, such as `ge`, `bd` or `3m`, only at the start of the maker), so `Acme GE Supply` is not GE. The reason of such a match says so (`"BD" and the recalling firm "Becton, Dickinson and Company" are the same company.`), and a maker of a family is also searched in openFDA under the family's main name (at most one more search per family). The list is short on purpose and comes from public acquisition history, not from a registry: a company that is missing is compared by its words, as before.
- **Model.** Looked for in both the product description and the code info.
- **Lot/serial.** Looked for in the code info only, since that is where FDA lists them.
- **Serial ranges.** `serial numbers 1000 through 1500`, `SN 2001-2500`, `serial number < 2224`, `serial numbers 3000 and above`. Read only from text that follows the word *serial* (or `S/N`, `SN`) and stops at the next `lot`, `;` or sentence end, so a lot code such as `Lots: 2011-2331` is never a range, and a "range" whose end is below its start (`2008-1459`) is a code too. A limit (`< 2224`) is applied only to a serial with the same number of digits, and a range to a serial whose length lies between its ends, because one recall often lists several products with a limit each (a 7-digit part serial is never judged by an 11-digit ventilator limit). A serial with letters after the digits is not a number and is never judged by a range. Code: [`src/serials.js`](../src/serials.js).
- **All units.** The recall's code info contains `all serial`, `all lot`, `all unexpired` or `all units` and is not followed (within four words) by a condition such as `with`, `running`, `version`, `manufactured between`: "all serial numbers with software versions 22D28..." is not every unit.
- **Device type** (weakest rule only). Every word of the device's type (`infusion pump`) appears in the recall's product text.

## The numbers, and why

There are no unexplained constants. All are named exports in [`src/matching.js`](../src/matching.js) or [`src/recallSearch.js`](../src/recallSearch.js):

| Constant | Value | Reason |
| --- | --- | --- |
| `MIN_MODEL_LENGTH` | 3 characters | A model like `A1` or `10` would "appear" in almost every recall by chance. |
| `MIN_LOT_LENGTH` | 4 characters | Same reason for lot/serial numbers. (A short serial that the text ties to the device's own UDI-DI is trusted anyway.) |
| `MIN_SERIAL_DIGITS` | 3 digits | A serial shorter than this is never judged by a range or limit (`serial < 2224` must not catch a serial `7`). |
| `MIN_MODEL_LENGTH_OTHER_MAKER` | 5 characters | The `possible-model-other-maker` rule ignores the manufacturer, so the model alone must be distinctive. |
| `LOOKBACK_DAYS` | 3 x 365 | Looks at the last three years: recalls often stay open (the FDA lists them as "Ongoing") long after they were issued, and a hospital still has the devices. |
| `UDIS_PER_QUERY` | 5 | One search per five identifiers (each written in up to three forms), to keep URLs short. |
| `MAX_PAGES_PER_QUERY` | 4 | A search with more matches than one answer holds is read page by page, up to 100 recalls; a search with still more is flagged as capped. |
| `MAX_CONCURRENT_REQUESTS` | 2 | openFDA allows about 240 requests a minute per address; two at a time stays well inside that and keeps the answers being parsed at once few (the live check ran out of memory at six). |
| `MODELS_PER_QUERY` | 5 | Keeps search URLs short and stops one very common model crowding out others. |
| `MAX_RECALLS_PER_QUERY` | 100 | openFDA's per-request maximum. |
| `SEARCH_LIMIT_PER_QUERY` | 25 | Recalls requested per page. Smaller is faster; 25 kept every match in the demo, and a busy search continues on the next page. |
| `CACHE_TTL_HOURS` | 6 | How long a saved check stays fresh. FDA publishes about weekly, so a few hours old is fine, and it spares openFDA's request limit. |
| `SEARCH_DEADLINE_MS` | 240 s | Gives up on slow searches 60 s before the 300 s limit of the background function. |
| `STALE_JOB_MS` | 6 min | A background job with no progress update for this long counts as failed. |
| `CHUNK_CHARS`, `MAX_CHUNKS` | 50,000 characters, 60 parts | Forge storage rejects any single value over 240 KiB, so a saved result is cut into parts (at most 150 KB each) with a small head record written last: 1,000 matches are about 10 parts. A result needing more than 60 parts (about 3 MB) is shown but not saved. |
| `MAX_JOB_COPY_BYTES` | 150 KiB | The job record keeps a copy of the finished result only while it fits in one value; a bigger one is read from the saved parts instead. |
| `MAX_IMPORT_ROWS` | 1,000 | One paste may hold this many devices; only the rows that changed are written, four groups of 25 at a time. Not yet timed on a live site at this size. |

## Ordering

Results are sorted by confidence (exact, likely, possible), then recall class (I is the most serious), then newest recall first, then device id, so the order is always the same.

## Several products in one recall, and exclusions

- **Per product.** A recall often covers several models in one code text. A device is judged only against the part of the code text that names **its** model (or UDI-DI), so a lot, a range or "all serial numbers" of one product never confirms another (`scopedRecall` in `src/matching.js`). Real recalls write one product as an *entry*, with its model, its UDI-DI and its lots in separate sentences ("1. Model Number: 44-0712. UDI-DI: (01)6088... Lot Code: 550031624. 2. Model Number: 44-0707. ..."), so the text is cut into entries first: at a label that carries a number (`Model No`, `Part No.`, `REF`, `Catalog Number`, `Product Code`) or at a list number (`2.`, `3)`), but only after the entry before it has said something about units, so `Model No 123, Catalog No 456, Lot A1234` stays one entry. Without such labels ("WX-200: all serial numbers. WX-300: lots C9999.") it falls back to the sentences that carry unit words. Either way the cut counts only when there are two or more parts with unit words and one of them names the device; otherwise the whole text is used. Known limits: a model named only in the product description (not in the code text) cannot be scoped, and an entry that starts with a bare number and a name and no label ("5855300 Slim-Cath ... Lot Number: REKY1364") cannot be cut.
- **Exclusions.** "All lot numbers except lot 12345" or "1000 through 1500, excluding 1200" name units that are *not* affected. When the part of the code text that names the device holds such a word (except, excluding, other than, not including, apart from) the unit-level rules are off for that product and the answer stays *likely*, so a person checks. The exclusion belongs to its own entry: in the real Maquet recall Z-0420-2024 one part is "a range minus six named serials" and the other lists those six, so the second part's serial is still *exact*.
- **Measured.** Both rules were found by independent review. The accuracy set now holds six real recalls with several products (27 pairs where a product's model or UDI-DI is paired with another product's lot: none is *exact*) and three that leave units out (7 units the text rules out: none is *exact*). Building it found two real defects, fixed: the first version of the per-product rule cut the text at every full stop and so judged real recalls (Cooper INCA, restor3d) against the wrong lots, and a UDI-DI written "UDI - 0403..." (with a dash) was not read at all.

## Known limits

- **Ruling a unit out (rule `possible-unit-ruled-out`).** When the product matches but the recall itself leaves this unit out, the answer drops from *likely* to *possible* (no task) in two cases only: the unit's serial is named in a plain list after "excluding" and appears nowhere else in the product's text, or the product's text states serial ranges or limits that apply to the serial (same letters, a length they can judge), the serial is outside all of them, and the whole code text has no lot or batch list, no "all units", no exclusion words, no "also included" or "updated to include" additions and no wording that limits units in a way we do not parse ("shipped before 2019", "software version", a date or a year). A review found a first, shorter list of such words too narrow, so the list is wide on purpose. The reason quotes the recall's own words and says no task is created. Everything else stays *likely*: a wrongly read range would hide a real recall, and a recall that adds units outside its own range (Z-0420-2024) must not be read as a closed list. On the labeled set 6 of the 9 units a recall rules out are ruled out and none of the 330 pairs that need a task is.
- **A very short serial needs a UDI-DI.** A serial or lot of fewer than four characters ("209") is not trusted on its own; recorded with the UDI-DI that the recall ties it to, it is **exact**.
- **UDI forms not yet read.** Only GS1 GTINs are read (8, 12, 13, 14 digits). HIBC codes (`+M335...`) and a DI that appears only in a picture are not.
- **Company families are a short list.** A maker that is not on it, or an old brand name that is not on it, is only found through its UDI-DI or its model number in the recall text. Two firms on the same list are treated as one company: the model, the serial and the kind of device still decide how sure the match is, so "Hospira" does not make every ICU Medical recall a match, but a family with a firm that is really separate would cost false "possible" matches (which create no task).
- **Very long code texts are cut at 150,000 characters** (about 15,000 serial numbers; one real recall has 8.9 million). Holding them all ran the live check out of memory. A unit whose serial is listed only beyond that point is not found by its serial; the UDI-DI and the model still find the recall.
- **No spelling variants.** `monitor` and `monitors` are different words, and `MMT1885CLW` does not match `MMT-1885CLW`.
- **At most 100 recalls per search.** A manufacturer or model group with more than 100 recalls in the three-year window may have older ones missed. The panel says so when any search hit this cap (openFDA reports the real total, so it is exact, not a guess). The model and UDI-DI searches still catch recalls that mention a hospital model or identifier.
- **openFDA rate limit, and how it grows with the list.** Anonymous use is limited (about 1,000 requests a day per IP address, 240 a minute, and Forge's outgoing addresses are shared, so the allowance is not the app's alone). A check plans one search per manufacturer, one per five models and one per five UDI-DIs, each read page by page when it has many recalls: 26 for the 30-device demo hospital (measured), and on the order of 120 to 400 for a list of 1,000 devices depending on how many different models and identifiers it has (planned with `planRecallQueries`, **never run** against the live API at that size). That is why a check runs on a button click and once a day, and why results are saved. The app reads an optional free openFDA API key (120,000 requests a day) from the environment variable `OPENFDA_API_KEY` (`forge variables set --encrypt OPENFDA_API_KEY <key> -e <environment>`); it is **not set** in the development or production environments of this submission.
- **The FDA is not the only source.** Recalls from other regulators are not included.

## How accurate is it?

Measured against 3,438 labeled pairs built from 48 real recalls, six of them naming several products, three leaving units out and nine with a maker that goes by two names: [ACCURACY.md](ACCURACY.md) (generated by `npm run eval`; `npm test` fails when it is out of date).
