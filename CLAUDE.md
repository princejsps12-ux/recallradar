# CLAUDE.md: RecallRadar

Forge app (Atlassian Codegeist 2026, Specialized Industries) for hospital teams: it matches FDA medical-device recalls (openFDA) to the hospital's devices and says how sure each match is and why. Shows as a panel on every Jira issue. User-facing docs are in [README.md](README.md); this file is what a new session needs to work safely.

`AGENTS.md` is generic Forge template guidance. **Where it conflicts with this file, this file wins.** In particular this app is **Custom UI (React) on purpose** (`static/ui/`), so AGENTS.md's "UI Kit only" rule does not apply here. Its security advice (minimal scopes, prefer `asUser`) still does.

## Testing rules

- **Look at UI changes in the preview first** (`npm run preview`, or `node scripts/preview/shot.cjs <view> <state> <theme>` and read the image), then run `npm run test:preview` before deploying: it catches what jsdom cannot (a component that the Forge iframe's CSP leaves unstyled, layout at a width, contrast, panel overflow) and reaches states the demo site cannot show (first run, errors, nothing affected). It is not Jira (system font, a fake backend): still check the final look on the demo site. Adding a resolver means adding it to `scripts/preview/backend.js` (a test fails otherwise).
- **Test on the Forge demo site only** (`--demo-site`; it has Rovo, Assets and sample Jira issues). The user's personal dev site is old and outdated: do not deploy to or test on it. Ask the user for an issue URL if you need one for a browser check.
- Use Claude in Chrome (the user's real, signed-in browser) for the site, not the built-in browser. Jira may show a one-time "What kind of work do you do?" screen: that sets an account preference, so leave it to the user.
- The demo site's MOBL project holds 35 RecallRadar test tasks from verifying task creation (find them with JQL `labels = recallradar`). Creating tasks again for the same recall + device is blocked by design, so to re-test creation the user must delete those first: ask, because deleting is theirs to approve.
- The panel sits in an iframe with its own scroll area; scroll inside it to see long content. Browser waits are capped at 10 s per step.

### The recall check is a background job

A Forge **UI function is cut off at 25 s and cannot be given a longer timeout** (`timeoutSeconds` is allowed only on queue consumers and scheduled triggers; the linter rejects it on a resolver). A cold check takes about 10 to 14 s on the site and could be slower, so:

1. The button calls resolver `startCheck`, which records a job and pushes `{ jobId, trigger }` onto the Forge queue `recall-check`, and **returns at once**.
2. `consumer.handler` (queue consumer, `timeoutSeconds: 300`) runs the check, writing progress to the job record after every search.
3. The panel polls `getCheckStatus` every 2 s and shows "Checked N of M FDA searches". A reload mid-check picks the job back up.
4. A finished check is saved (6-hour freshness). On open, the panel shows the saved result at once; if it has **expired** it is shown flagged "older than 6 hours" and a background refresh starts automatically.
5. A daily scheduled trigger (`scheduled.handler`) refreshes the saved result so it is usually ready before anyone clicks.

Rules that keep this correct: a result with failed lookups is shown but never saved; only the running job with the matching id may be updated (late or duplicate queue deliveries are skipped); a job with no update for 6 minutes counts as failed; the search has its own 240 s deadline inside the 300 s limit.

### Daily alerts (`src/alert*.js`, docs/ALERTS.md)

The daily trigger runs the check, then `runDailyAlerts()`. A "new" pair is an exact/likely match of an open recall that was not in the `alerts:state` record at the last complete check; the first look, devices imported/loaded (`devicesChanged`) and switching alerts on (`rebaseline`) are baselines, never alerts. **`asApp`** is used only here (a schedule has no person): saving the settings runs `taskIssueTypeId` as the app, so a project the app user cannot use is refused at once with `friendlyJiraError`. Never store an account id or name in `alerts:*` (privacy rule). New Atlaskit packages `@atlaskit/toggle` and `@atlaskit/textfield` (compiled CSS, no emotion: the preview check proves the CSP). Live verification on the demo site is in the README ("What was and was not verified").

### The Rovo agent (RecallRadar Assistant)

Six actions (`list_open_recalls`, `check_device`, `create_remediation_tasks`, `recall_details`, `create_recall_page`, `who_handles_ward`) plus a `rovo:skill` (`recall-triage`, `skills/recall-triage/SKILL.md`). Logic is pure in `src/agentTools.js`; `src/rovoActions.js` is the Forge handler layer.

- **Saved results only**: tools read `loadSnapshot()` (devices + latest saved check, fresh or expired); they never call openFDA. Saved results carry `recallDetails` (status, initiated, reason per recall) for explanations: a check saved before that change has none until refreshed.
- **Every answer has `citations`** (the only recall numbers / device ids the agent may quote). Keep that: the "never invent" promise rests on it plus the agent prompt in `manifest.yml`.
- **Preview then confirm** for task creation: no confirmed flag means preview only and a one-use, 10-minute `confirmationToken`; confirming creates exactly the previewed pairs. Rovo also shows its own "Please review" card for any `actionVerb: CREATE` action (two approvals in practice). Tasks are created as the chatting user. Optional `assignSuggested` (preview only) stores ONLY the flag in the preview record; at confirm time `assigneesForMatches` looks the people up again. **Never store an accountId or a name in Forge storage** (a privacy promise in the README and PRIVACY.md: previews, guards and caches hold ids of devices/recalls only).
- Rovo action quirks: inputs are **primitives only** (string, integer, number, boolean); an action `description` is **max 255 characters** and must be **quoted in YAML if it contains `: `**; function keys must be short (`create-remediation-tasks-fn` was rejected as too long, keep to about 20 characters); inputs arrive directly on the payload (with `context`, `orgId`, `contextToken` beside them).
- Testing the agent: **Ask Rovo** from a Jira page (sidebar) or **Rovo Home** (home.atlassian.com, which "Switch to: Full screen" opens); open the agent picker and click into its "Search agents" box BEFORE typing (typing with the picker open but unfocused fires Jira keyboard shortcuts: `c` opens Create issue). The app has ONE installation per site (see "One installation for Jira + Confluence" below), so the picker lists **RecallRadar Assistant once** and every chat reads the same devices. The log line `Rovo action X: input keys [...]` is the only trace of a call. (The Forge function context's `installContext` says `confluence` for a Rovo Home call even though the storage is the shared one: do not branch on it.) Before 2026-11-16 the app had separate Jira and Confluence installations: two agents in the picker, and Rovo Home reached the empty Confluence one. The demo hospital's ICU devices have no Class I recall: use the Cath Lab (Impella) or Respiratory (Astral) for Class I questions (the starters do).

### Confluence recall pages (`create_recall_page`)

`src/recallPage.js` (pure XHTML builder, everything escaped) + `src/recallPageService.js` + `src/confluenceClient.js`. One page per open exact/likely recall, titled `FDA recall <number>`, **found again by title inside the space and updated** (never duplicated). ### Teamwork Graph (read-only; writes decided: skip)

The user decided **not to write to the graph**; do not start that again unprompted. The app **only reads** it (a Codegeist bonus also counts read-only apps). Never click the connection's legal consent for the user.

Probe findings are in `docs/teamwork-graph-findings.md`; do not redo them. Key facts: reading needs a **user** context (`api.asUser().requestTeamworkGraph(query, variables, operationName)`, no `asApp`, so **never from the queue consumer or daily trigger**), an operation name shaped `company_operation` (in the query text and as the 3rd argument), and union fragments (`... on AtlassianTeam`); there is **no team owner/role field** and **no "list all teams" query**; writing needs an admin connection with a consent dialog. The caller's account id is `context.accountId` in resolvers, `context.principal.accountId` in Rovo actions.

The feature (all pure and unit tested, Forge only in `runtime.js`/`index.js`/`rovoActions.js`):

- `src/teamGraph.js`: the **only four calls** (`atlassianUserInTeams`, `atlassianTeamMembers`, `spacesByAtlassianTeam`, `atlassianUserAssignedJiraWorkItems`). docs/TEAMWORK_GRAPH.md lists them verbatim: if you change a query, change that page and the README section "Teamwork Graph (read-only)" too. Scopes `read:graph:team:atlassian`, `read:graph:user:atlassian`, `read:graph:project:jira`, `read:graph:issue:jira` (the last two were added 2026-11-17 = a major version: deploy with `--approve MAJOR_VERSION_RULE`, then `install --upgrade ... --confirm-scopes` on every site). The graph does NOT error on a missing scope, it leaves rows out: an empty answer can mean "scope not granted". `teamService.wardOwnership` + resolver `getWardPeople` feed the drawer card `WardPeople.js` (read when opened, kept only in page memory, never stored) and `who_handles_ward` (`worksIn`, `openWorkPerPerson`, left out when the graph cannot say). The suggestion rule did not change.
- `src/wardTeams.js`: ward to team mapping, one Forge-storage record (`ward-teams`), wards compared with `compact()`.
- `src/teamService.js`: `SUGGESTION_RULE` (fewest open RecallRadar tasks, then first name), `setWardTeam` (team must be in the caller's graph teams; the **name comes from the graph**), `assigneesForMatches`, `checkExplicitAssignees`, `whoHandlesWard`.
- **Ask before assigning**: nothing is assigned by default. The panel sends only account ids; the server re-checks each against the ward's team (`checkExplicitAssignees`) before `createTasks({ assignees })`. Graph down means tasks are created **unassigned** with a note, never blocked.
- Resolvers: `getWardTeams` (storage only, no graph call), `listTeams`, `setWardTeam`, `suggestAssignees`, `createTasks` with `assignees`.
- Verified live: mapping, team line, suggestions, `who_handles_ward`. The API **rejects `first` above 25** (page size is 25). One real assignment verified live (MOBL-99); the "create all" checkbox was not clicked. Assigning notifies people: ask first. The demo site now maps ICU, Cath Lab and Cardiology to Team Atlas.

### Jira tasks for matches

Only **exact** and **likely** matches get a task. Due date is calendar days from creation (UTC): Class I 2, Class II/III 7, unknown class 2 (treated as Class I); the numbers and reasons live in `taskRules.js` and the README, so change them there and in the README together.

- **Never a duplicate**: every task has a label `recallradar-<recall>-<device>`. Creation first searches Jira by label (Jira is the source of truth, so it survives cleared storage and other browsers), plus a 2-minute guard in Forge storage for Jira's search-index lag. Keep both layers.
- **The server rebuilds each task from the saved check result**; the browser sends only `{ recallNumber, deviceId }`. Never accept task text or dates from the page.
- Tasks are created **as the clicking user** (`asUser`, scope `write:jira-work`) in the project of the issue the panel is open on, via Jira's bulk endpoint (max 50 per call).
- **Request size**: about 0.6 s per task and a UI function dies at 25 s (34 tasks took ~20 s). The server caps a request at 25 pairs (`MAX_PAIRS_PER_REQUEST`) and the panel sends batches of 10. Do not raise either without re-measuring.
- Links: the openFDA record URL for the recall number is the only per-recall link that was verified. FDA's own pages (`ires`, `res.cfm`) return 200 but could not be shown to display the specific recall.

### Privacy rules the code must keep

- **No personal data in Forge storage**: no accountId, name or email anywhere (`ward-teams` holds team ARI and team name only).
- **Retention**: the saved check and the finished job (it holds a copy) at most **24 hours**; previews 10 minutes and task guards 2 minutes, **deleted** (not just ignored) when they expire: on read, on the next write, and by `cleanupStorage()` in the daily trigger. If you add a new stored record, give it an expiry and add it to `cleanupStorage()`, the tests, README "Data and trust" and `marketplace/PRIVACY.md`.

## Gotchas learned the hard way

- **Jira's Custom UI iframe ignores a `<style>` element** (CSP), so anything that writes its styles at run time renders UNSTYLED (proved in `scripts/preview/csp-probe.js`: a `<style>` tag, even an empty one filled with `insertRule` as emotion does in production, and `setAttribute('style')` are blocked; `element.style.x =` (React style props), constructable stylesheets and a same-origin `<link>` work). Atlaskit's NEW components (`@atlaskit/button/new`, Lozenge, Select, Modal, Tabs...) ship their CSS as a normal stylesheet and are fine. Anything built on the LEGACY button or on emotion is not: `@atlaskit/pagination` and the pager inside `DynamicTable` draw their buttons with the legacy `@atlaskit/button/standard-button` and came out as plain browser buttons in Jira. Handing `Pagination` our own button components fixed the look but not the cause (the legacy Button still tried to write its blocked styles on every render), so `ui/Pager.js` is a plain `nav` + list of new Buttons (which numbers to show: `pageWindow` in `tablePaging.mjs`, unit tested), and tables that can have more than one page use `DynamicTableStateless` + `Pager` (never `DynamicTable`'s `rowsPerPage`). The supported escape hatch is `permissions.content.styles: ['unsafe-inline']` in manifest.yml ([docs](https://developer.atlassian.com/platform/forge/manifest-reference/permissions)); we do NOT use it (it loosens the policy for every module and is a permissions change). How to catch this before a deploy: `npm run test:preview` serves the real bundle under such a policy and FAILS on any violation (one is known and accepted: opening a dialog makes `react-scrolllock` inside `@atlaskit/modal-dialog` write a `body` style, so the page behind a dialog can still scroll). Before adding any Atlaskit component, check its dist code: an import of `@emotion/react` or `standard-button` is suspect. Otherwise only inline `style="..."` props work, and visually-hidden text must be inline-styled. The jsdom smoke test cannot see any of this: use the preview or look at the live page.

- **Never create a `tsconfig.json` at the repository root.** Forge's own linter (run by `forge lint` and by `forge deploy`) finds it, makes typescript-eslint use it and then fails because it does not include every linted file (the tests, the scripts): the deploy stops. The type-check configs are `tsconfig.check.json` and `tsconfig.check.strict.json` for that reason.
- **`route` template**: only interpolate single path *segments* (ids). Interpolating a value that contains `/` throws "Disallowing path manipulation attempt".
- **`@forge/api` has no `storage`** in this version: use `@forge/kvs` (`kvs.get/set/delete/query`), scope `storage:app`.
- **Queue consumer events** carry data in `event.body` (not `payload`); `queue.push({ body })` wraps the data.
- **Scheduled triggers DO run in the development environment** (verified: with `interval: fiveMinute` the first run came about 3 minutes after the deploy, then every 5 minutes). The shortest interval is `fiveMinute`. If you ever test one that way, **restore `interval: day` before leaving it**: a 5-minute trigger makes ~24 openFDA requests per run and blows through the daily limit. Changing any scheduled trigger resets all start times.
- **Scopes/egress changes make a major version** and need `--approve MAJOR_VERSION_RULE` plus `install --upgrade`. Adding the `api.fda.gov` egress made the app **ineligible for Runs on Atlassian** (a Codegeist bonus, if it applies: check the rules).
- **openFDA**: use `/device/enforcement.json` (it has recall number, firm, product, `code_info`, `classification`, `report_date`; the `/device/recall` endpoint has no class). Dates are `YYYYMMDD`. A search with no hits returns **404** (treat as empty). `code_info` can hold thousands of serials; one record (Z-1645-2026) is 8.7 MB because of an unused `openfda` sub-object, and openFDA cannot omit fields. Anonymous limit is about 1,000 requests a day per IP (a full check is about 24), which is why results are saved. Newest 100 recalls span only about a week, so match by manufacturer/model within a date window, never by "latest N".
- **Assets**: Forge can *read* Assets as the app (`read:cmdb-object:jira`, `read:cmdb-schema:jira`, workspace id from `/rest/servicedeskapi/assets/workspace`) but *creating* a schema returned 403 (Assets-administrator rights). Hence devices live in Forge storage; the unused Assets scopes were REMOVED from the manifest (least privilege); re-add them when the import is built.
- **An invented serial can collide with a real one**: when adding demo devices, check them against the real recall (`scripts/check-demo-matches.mjs`).
- `forge webtrigger create` has no `--non-interactive` flag. `forge lint --fix` converts deprecated manifest forms.
- A free developer site has no Rovo chat; the demo site does.

- **One installation for Jira + Confluence (multi-app compatibility, since 2026-11-16).** `app.compatibility` in manifest.yml makes Jira the required app and Confluence an optional connection ([docs](https://developer.atlassian.com/platform/forge/app-compatibility/), [migration guide](https://developer.atlassian.com/platform/forge/migrating-a-forge-app-to-support-multiple-atlassian-apps/)): one installation id and one storage per site, one agent in the picker, Rovo Home reads the same devices. Facts that cost time: (1) `forge deploy` REFUSES an environment that still has an installation in a non-required product ("Unable to deploy an app to an environment with an existing installation in an Atlassian app that is not the required Atlassian app"), so the old separate Confluence installation had to be uninstalled first; `forge uninstall -e <env> -s <site> -p Confluence` has no `--non-interactive` flag and needs no confirmation; uninstall order is optional apps first, Jira last. (2) It is a minor version while no scopes change; existing Jira installations keep their data. (3) It cannot be reverted while any installation exists, and **Atlassian only allows PAID Marketplace listings for such apps** (marketplace/SUBMIT.md used to say Free: the owner decides, see SUBMIT.md). (4) `forge install list` shows one row with "Jira (required)" and "Confluence" under "Connected to"; the admin page's Confluence row can say "Connecting..." for minutes after the CLI already shows it connected. (5) The Claude Code auto-mode classifier blocks `forge uninstall` and a `forge deploy -e staging` until the user says yes in chat: ask first. (6) The public install link carries `&product=jira&product=confluence`: how it behaves in this mode is in README (Judge quick start) once verified on a clean site.
- **Forge panel (Custom UI) will not load if the machine's DNS refuses Forge's CDN host.** Symptom: the panel stays a grey skeleton and the console says `Failed to open iframe bridge ... Handshake timeout`. Check: `dig <host>.cdn.prod.atlassian-dev.net` (host from the iframe `src`) returns `status: REFUSED` on the system resolver but resolves via `@1.1.1.1`. Not an app bug (an old bundle failed identically); fix is the user's network or DNS. Rovo chat and resolvers still work.
- **UI smoke test without a browser**: `npm run test:ui` (`scripts/ui-smoke.cjs`) renders the real panel and dashboard in jsdom with a stubbed `@forge/bridge`, clicks the main flows (first run, filters, import, errors) and exits non-zero on a failure. Use it when the Chrome tool or the live panel is unreachable. It cannot judge looks.

## Layout and naming (changed 2026-11-16)

The Custom UI lives in `static/ui/` (it was the template's `static/hello-world`), the issue panel's module key is `recallradar-panel`, the packages are `recallradar` and `recallradar-ui`, and `@forge/api` is the stable 8.5.0. The long README was split: it keeps the judge path and the features, and the engineering detail is in `docs/` (MATCHING, ARCHITECTURE, TASKS, TEAMWORK_GRAPH, MCP, DEVELOPMENT; the Teamwork Graph queries in docs/TEAMWORK_GRAPH.md must stay verbatim with `src/teamGraph.js`). ## Conventions

- **Commit per finished part**, message in plain imperative English, ending with the `Co-Authored-By` trailer the harness gives. Never commit build output or `node_modules` (see `.gitignore`).
- Code comments explain *why*; no unexplained numbers (named constants with a reason). Every matching rule and every cache/job rule has unit tests, including cases that must **not** match.
- Keep the README honest: measurements, limits and "not built" lists are part of it. Update both README and this file when behavior changes.
- The user prefers short explanations before running each step, and a stop for decisions that are theirs (account preferences, new sites, anything that spends money or is outward-facing).
